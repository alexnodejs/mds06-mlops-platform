## 0. Що змінилось у стеку

До Теми 11 реєстр був полицею: версії лягали, аліас `@champion` вказував на
останню, і на цьому все. Три речі, яких бракувало, і які тепер є:

```
      ДАНІ                    РЕЄСТР                     ДЕПЛОЙ
 s3://datasets/          iris-rf v7                  Service ml-model
   iris/v1.csv    ──►      tags: dataset,      ──►      selector:
   iris/v2.csv             git_sha, ...                   variant: blue
   iris/v3.csv             @challenger                        │
                           @champion  ──────────────────►  blue  (@champion)
                           @previous                       green (@challenger)
```

| | Було | Стало |
|---|---|---|
| Дані | `load_iris()` в образі | CSV у MinIO, три версії |
| Звʼязок із даними | немає | `mlflow.log_input` + digest |
| Звʼязок із кодом | немає | тег `git_sha` |
| Статуси | лише `@champion` | `@challenger` → `@champion` → `@previous` |
| Відкат | вручну шукати номер | `make rollback` |
| Деплой | замінити модель на місці | blue-green із перемиканням |

## 2. Дані переїхали у сховище (слайд 16)

### Три версії, і кожна з них потрібна

```bash
make seed        # кладе всі три в MinIO
```

| Ключ | Рядків | Навіщо |
|---|---|---|
| `datasets/iris/v1.csv` | 150 | оригінал — «як було до Теми 11» |
| `datasets/iris/v2.csv` | 1500 | робочий: ресемплінг + шум |
| `datasets/iris/v3.csv` | 1500 | `petal_length` зсунуто — дані «поїхали» |

**Навіщо 1500 замість 150** — не заради розміру. На 150 рядках тест забирає 30, і
f1 фізично може набувати лише трьох значень:

| помилок із 30 | f1 |
|---|---|
| 3 | 0.8997 |
| 2 | 0.9333 |
| 1 | 0.9666 |

Крок **0.033** при порозі промоції `MIN_DELTA = 0.001`. Тобто quality gate Теми
10 весь цей час порівнював **шум**: різниця в одну помилку на тридцяти зразках —
це випадковість, а не якість. На 1500 рядках тест — 300, крок ≈ **0.003**, і
поріг нарешті щось означає.

### Lineage — рідним API MLflow, а не тегом

```python
ds = mlflow.data.from_pandas(df, source=DATASET_URI, name="iris", targets="target")
mlflow.log_input(ds, context="training")
```

`log_input` рахує **digest** — хеш вмісту — і зберігає схему та профіль. У MLflow
UI зʼявляється вкладка **Datasets** у запуску.

Чому digest, а не шлях: імена й шляхи брешуть. `iris/v2.csv` сьогодні й
`iris/v2.csv` через місяць — це два різні файли, якщо хтось перезалив бакет.
Хеш це показує, шлях — ні.

### ⚠️ Пастка, яку варто показати студентам

```python
s3 = boto3.client("s3", endpoint_url=os.getenv("MLFLOW_S3_ENDPOINT_URL"))
#                        ▲ ЯВНО, і без цього все ламається мовчки
```

`MLFLOW_S3_ENDPOINT_URL` — змінна **MLflow**, а не botocore. MLflow читає її сам
і передає в boto3 параметром. `boto3.client("s3")` без `endpoint_url` піде у
**справжній AWS S3** із ключами `minioadmin`, отримає 403 — і виглядатиме це як
«зламався MinIO».

## 3. Метадані версії (слайди 14-16)

Слайд 16: «модель — не ізольований файл». Тепер кожна версія несе теги:

| Тег | Приклад | Відповідає на питання |
|---|---|---|
| `dataset` | `s3://datasets/iris/v2.csv` | на яких даних |
| `dataset_digest` | `a3f21c9e...` | чи це той самий файл |
| `git_sha` | `4ca1ae2b5cdc` | з якого коду |
| `trained_by` | `github-actions` | хто запустив |
| `status` | `production` | у якому вона стані |

Плюс `description` — те, що людина читає першим, відкривши версію в UI.

Перевірити:

```bash
curl -s "localhost:5001/api/2.0/mlflow/model-versions/get?name=iris-rf&version=1" \
  | python3 -m json.tool | grep -A20 tags
```

Те саме видно на сторінці сервісу http://localhost:8000 — таблиця «Звідки
взялась ця модель».

> 🔴 **`git_sha` доти губився.** Пайплайн Теми 10 отримував `commit_sha` з CI,
> валідував його — і використовував лише в **імені Job-а**. У MLflow він не
> потрапляв узагалі. Тепер їде через `state_machine.asl.json` у змінну пода.

## 4. Статуси: слайд каже Staging, MLflow каже аліас (слайд 15)

Слайд 15 називає чотири статуси: Draft, Staging, Production, Archived. У MLflow
3.x **stage-и застарілі** — офіційна заміна це аліаси. Мапа один в один:

| Слайд 15 | У нас | Хто ставить |
|---|---|---|
| Draft | тег `status=draft`, аліаса немає | `train.py` при реєстрації |
| Staging | аліас **`@challenger`** | `train.py`, коли `PROMOTE_TO_CHAMPION=false` |
| Production | аліас **`@champion`** | `promote.py` після quality gate |
| Archived | тег `status=archived` + `@previous` | `promote.py` для попереднього |

**Чому аліаси кращі за stage-и:** stage — це властивість версії («ця версія в
Production»), і кожна модель могла мати лише один набір фіксованих назв. Аліас —
це **вказівник**, і їх можна мати скільки завгодно: `@champion`, `@challenger`,
`@shadow`, `@eu-west`. Код у проді просить `models:/iris-rf@champion` і не знає
ні номера версії, ні шляху в MinIO.

## 5. Хто і коли оновлює модель (слайд 22)

| Роль зі слайда | У нашому стеку |
|---|---|
| Data Scientist тренує й відправляє кандидата | `make train PROMOTE=false` → `@challenger` |
| MLOps Engineer перевіряє інтеграцію | green піднімається на кандидаті, метрики порівнюються |
| Reviewer / система вирішує | quality gate Теми 10 або коміт у `service.yaml` |

Слайд 22 називає чотири приводи оновити модель. Три з них у стеку є:

- **за розкладом** — `on: schedule` у GitHub Actions (не увімкнено, але тригер готовий);
- **при data drift** — дашборд дріфту Теми 9;
- **при поліпшенні** — quality gate Теми 10;
- **вручну** — `make train`.

**Про доступ.** Слайд 22 говорить про ролі й права. У навчальному стеку їх немає
свідомо: MLflow піднятий без автентифікації, і будь-хто з тунелем може
перевісити аліас. У проді це закривають на рівні MLflow (auth) або відбирають
право писати в реєстр у всіх, крім CI, — і тоді єдиний шлях у прод лежить через
пайплайн. Варто сказати вголос: **наш стек навмисно відкритий, і це не зразок**.

## 6. Відкат (слайд 14)

```bash
make rollback              # повернути @champion на @previous
make rollback VERSION=3    # на конкретну версію
```

`promote.py` при кожній промоції зберігає попереднього чемпіона аліасом
`@previous` і ставить йому `status=archived`. Тому відкат — не пошук номера в UI,
а одна команда.

**Відкат і промоція — це буквально одна операція**, лише з іншим номером версії:
`make rollback` запускає той самий `promote.py`, що й крок `PromoteModel` у Step
Functions. Окремого механізму відкату не існує — і це не спрощення. Якщо відкат
іде іншим шляхом, ніж викочування, він і ламається окремо, причому саме тоді,
коли він потрібен.

Сервіс підхопить зміну за ≤30 с (`MODEL_RELOAD_SECONDS`), або миттєво через
`POST /reload`, який `promote.py` смикає сам.

## 7. Деплой без перезбірки образу (слайди 27-29)

Слайд 27 описує класичний підхід: модель лежить у Docker-образі, і щоб її
оновити, образ треба перезібрати. Слайд 28 пропонує альтернативу: у образі лише
код, модель тягнеться з реєстру.

**У цьому стеку працюють обидва — і другий страхує перший:**

```python
# apps/model-api/app.py
model = mlflow.sklearn.load_model(f"models:/{MODEL_NAME}@{MODEL_ALIAS}")
```

Якщо MLflow недоступний, сервіс лишається на `model.pkl`, зашитому в образ
(`source: "baked"` у `/healthz`). Це не костур, а свідомий резерв: падіння MLflow
не має класти інференс.

⚠️ **`load_model` не можна викликати на старті синхронно.** Це коштувало одного
розгортання: MLflow піднімається пізніше за модель, HTTP-клієнт висить на
ретраях, порт 8000 не відкривається, liveness валить под. Перше читання реєстру
робить фоновий потік. Урок ширший за цей файл: **`try/except` рятує від винятку,
а не від зависання**.

## 8. Blue-Green (слайд 35)

### Як це влаштовано

```
Service ml-model  selector: variant=blue  ← ПЕРЕМИКАЧ (весь бойовий трафік)
   ├─ Deployment ml-model         variant=blue   @champion    2 репліки
   └─ Deployment ml-model-green   variant=green  @challenger  0 реплік

Service ml-model-blue   selector: variant=blue   ← лише для скрейпу
Service ml-model-green  selector: variant=green  ← скрейп + ціль тіні
```

Перемикання — **один рядок** у `k8s/model-api/service.yaml`.

### Три рішення, які варто пояснити

**1. Селектор Deployment не змінювався.** `spec.selector` імутабельний, а лейбли
шаблона пода — ні. Селектор має бути **підмножиною** лейблів шаблона, тому
`variant: blue` додався без жодних наслідків.

Якби ми спробували додати `variant` у селектор, сталося б найгірше з можливого:
Service у тому самому коміті переїхав би на `variant: blue` **успішно**, а
Deployment упав би з `field is immutable` → порожні Endpoints → 100% помилок на
`/predict`, поки хтось не помітить червоний Application.

**2. У green інший `app`.** Не `ml-model`, а `ml-model-green`. Alloy кладе лейбл
пода `app` у мітку Loki, а дріфт-експортер читає рівно `{app="ml-model"}`. Зі
спільним `app` він змішав би прогнози champion і challenger в одному хі-квадраті,
а вікно 3000 записів подвоїлось би — при ліміті Loki 5000 воно почало б мовчки
обрізатись.

**3. Скрейп не залежить від перемикання.** Два окремі Service існують лише щоб
Prometheus бачив **обидва** варіанти завжди. Інакше після перемикання метрики
blue зникли б — а дивитись треба саме на них, вирішуючи, відкочуватись чи ні.

Лейбл `variant` потрапляє на метрики через `podTargetLabels` у ServiceMonitor —
**`app.py` не змінювався взагалі**.

⚠️ `jobLabel: app` у тому ж файлі — не косметика. Без нього `job` береться з
імені Service і став би `ml-model-blue`, а всі наявні запити з `job="ml-model"`
мовчки перестали б знаходити дані.

### Команди

```bash
make bluegreen-up      # green + тіньовий трафік (той самий payload в обидва)
make bluegreen         # хто де, яка модель у якому варіанті
make bluegreen-down    # прибрати
```

## 9. A/B і Canary — коли вони, а не Blue-Green (слайди 33-34)

Наживо реалізовано Blue-Green. Решта — тут, із командами.

### Canary (слайд 34)

Частка трафіку задається **кількістю реплік**: Service селектує спільний лейбл,
kube-proxy розкидає порівну по подах.

```yaml
# service.yaml — селектувати ОБИДВА варіанти
spec:
  selector:
    app: ml-model        # замість variant: blue
```
```bash
kubectl -n ml-demo scale deploy/ml-model --replicas=4        # 80%
kubectl -n ml-demo scale deploy/ml-model-green --replicas=1  # 20%
```

Крок — одна репліка, тобто мінімум 1/(N+1). Тонше — лише Argo Rollouts або Istio.

**Коли Canary:** зміна ризикована, відкат має бути дешевим, і є час спостерігати.
**Коли ні:** якщо дві версії не можуть співіснувати (несумісна схема даних).

### A/B (слайд 33)

Відрізняється від canary **метою**: canary питає «чи не зламалось», A/B —
«яка модель приносить більше користі». Тому A/B потрібен не рівний трафік, а
**стійке призначення користувача** до групи: той самий клієнт має весь час
бачити ту саму модель, інакше метрику неможливо порівняти.

У FastAPI це логіка в `/predict`:

```python
group = "b" if int(hashlib.md5(user_id.encode()).hexdigest(), 16) % 100 < 20 else "a"
```

Хеш від `user_id`, а не `random()`: інакше користувач стрибає між моделями.

**У нашому стеку A/B не реалізований**, бо в Iris немає користувача — генератор
шле анонімні квіти. Це чесна межа прикладу.

### Порівняння

| | Blue-Green | Canary | A/B |
|---|---|---|---|
| Питання | «перемкнути?» | «чи не зламалось?» | «яка краща для бізнесу?» |
| Трафік | 0% або 100% | 5% → 50% → 100% | фіксована частка |
| Відкат | миттєвий | зменшити репліки | вимкнути гілку |
| Ресурси | ×2 | +1 под | ×1 |
| Треба | нічого | нічого | ідентифікатор користувача |

## 10. Сценарій заняття

```bash
make up                       # стек + датасети + перша модель
make bluegreen-up             # green у тіні
```

### Прогін 1 — «звідки взялась ця модель»

http://localhost:8000 → таблиця «Звідки взялась ця модель»: дані, хеш, коміт,
хто, статус. Порівняти з тим, що показувала та сама сторінка в Темі 9 — там був
лише номер версії.

### Прогін 2 — кандидат

```bash
make train N=10 D=1 PROMOTE=false
```

`@challenger` вказує на свідомо гіршу модель. Green підхопить її за ≤30 с —
у Grafana, панель «Яка модель у якому варіанті», його `version` зміниться.

### Прогін 3 — порівняння варіантів

Grafana → «Blue vs Green». Дві лінії: blue тримає бойовий трафік, green — лише
тіньовий. Впевненість у green помітно нижча.

### Прогін 4 — перемикання

Спершу **антиприклад**:

```bash
kubectl -n ml-demo patch svc ml-model -p '{"spec":{"selector":{"variant":"green"}}}'
kubectl -n ml-demo get svc ml-model -o jsonpath='{.spec.selector}{"\n"}' -w
```

ArgoCD відкотить за кілька секунд. Git виграв.

Як треба — комітом:

```bash
# k8s/model-api/service.yaml: variant: blue -> green
git commit -am "blue-green: перемикаємо на green" && git push
kubectl -n argocd patch app ml-model --type merge \
  -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"hard"}}}'
```

⚠️ **Перезапустіть `make ports`.** `port-forward svc/` прибивається до одного
пода на весь час тунелю: після перемикання старий тунель і далі стукає в blue, і
«перемкнули, а версія не змінилась» зʼїсть десять хвилин.

### Прогін 5 — відкат

```bash
git revert HEAD && git push     # трафік назад на blue
make rollback                   # і модель назад на попередню версію
```

Дві різні речі, і це варто підкреслити: `git revert` повертає **трафік**,
`make rollback` — **модель**. Blue-green керує тим, який под відповідає; реєстр —
тим, яку модель цей под завантажив.

### Прогін 6 — дані вирішують

```bash
make pipeline-run              # на v2 → ПРОМОУТ
make pipeline-run DATASET=v3   # на зсунутих даних → ВІДХИЛЕНО
```

Уперше в курсі quality gate судить **зміну даних**, а не випадковість на 30
рядках.

| 15 | статуси Draft/Staging/Production/Archived | у MLflow 3.x stage-и **deprecated**; заміна — аліаси. Мапа в розділі 4 |
| 28 | «модель втягується під час старту контейнера» | у нас **не на старті**: синхронне читання на старті вішає под, коли MLflow ще піднімається. Читає фоновий потік |
| 29 | `mlflow.pyfunc.load_model()` | у нас `mlflow.sklearn.load_model()`: потрібен `predict_proba` для метрики впевненості, а pyfunc віддає лише клас |
| 32 | «Registry призначає версії й зберігає статус» | версії — так; статус — тегом, бо stage-и застарілі |
| 33 | A/B «логіка на рівні маршруту /predict» | не реалізовано: в Iris немає користувача, якого можна закріпити за групою. Пояснення в розділі 9 |
| 34 | Canary «через ваги в Service або ingress» | у голому Kubernetes ваг у Service **немає**; частка задається кількістю реплік. Ваги — це Istio або Argo Rollouts |

## 12. Типові помилки

| Симптом | Причина | Що робити |
|---|---|---|
| `dataset_unavailable` у логах Job | датасетів немає в MinIO | `make seed` |
| Тренування пройшло, але теги порожні | `GIT_SHA`/`TRAINED_BY` не передані | локально їх ставить `train.sh`; у пайплайні — `state_machine.asl.json` |
| `403` від S3 при читанні датасету | `boto3.client("s3")` без `endpoint_url` пішов у справжній AWS | передати `endpoint_url` явно |
| Дріфт показує 1 на спокійному трафіку | еталон і тренування на різних даних | звірити `DATASET_URI` у `drift-exporter.yaml` і в Job |
| `reference_source{source="builtin"}` | експортер не дістав датасет | перевірити секрет `mlflow-credentials` у ns `mlflow` |
| Green показує `source="baked"` | аліаса `@challenger` немає | `make train N=10 D=1 PROMOTE=false` |
| Після перемикання версія не змінилась | старий `port-forward` тримає под blue | `make ports` |
| `kubectl patch svc` відкочується | ArgoCD selfHeal — так і має бути | перемикати комітом |
| `field is immutable` на Deployment | хтось додав `variant` у `spec.selector` | селектор чіпати не можна, лише лейбли шаблона |
| Метрики blue і green злились | немає `podTargetLabels` у ServiceMonitor | додати; лейбл береться з пода |
| Панелі спорожніли після Теми 11 | немає `jobLabel: app` — `job` став іменем Service | додати `jobLabel: app` |
| `make rollback` каже «нема куди» | `@previous` зʼявляється лише після першої заміни чемпіона | `make rollback VERSION=N` |
