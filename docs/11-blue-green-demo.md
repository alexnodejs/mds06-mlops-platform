# Blue-Green: покроковий сценарій заняття

> Тримайте цей файл на другому екрані. Усі числа нижче **зміряні** на живому
> кластері, а не оцінені. Повний розбір, чому воно влаштоване саме так —
> [11-model-registry.md, розділ 8](11-model-registry.md#8-blue-green-слайд-35).

**Тривалість:** 20–25 хвилин. **Готування:** 5 хвилин до заняття.

---

## Підготовка (до заняття)

```bash
make up                 # якщо стек не піднятий
make ports              # тунелі
make bluegreen-up       # green + тіньовий трафік
```

### 🚦 Гейт 1: кандидат мусить бути ПОМІТНО гіршим

Це найважливіший крок підготовки, і його легко пропустити. Якщо blue і green
крутять моделі однакової якості, усі панелі виглядатимуть ідентично і
демонстрація провалиться.

Зміряно на реальних версіях: v8 (f1 = 0.9800) проти v23 (f1 = 0.9770) дали
впевненість **0.9687 проти 0.9713** — на графіку не відрізнити.

```bash
make train N=10 D=1 PROMOTE=false     # десять дерев глибиною 1
```

Дає f1 ≈ 0.71 і аліас `@challenger`. Green підхопить за ≤30 с.

### 🚦 Гейт 2: переконайтесь, що все на місці

```bash
make bluegreen
```

Мусить показати різні версії у blue і green. Якщо в green `source="baked"` —
аліаса `@challenger` немає, поверніться до гейта 1.

Зачекайте ~2 хвилини, щоб метрики накопичились, і перевірте, що різниця видима:

```bash
curl -s --data-urlencode 'query=sum by (variant) (rate(predict_confidence_sum{namespace="ml-demo"}[5m])) / sum by (variant) (rate(predict_confidence_count{namespace="ml-demo"}[5m]))' \
  http://localhost:9090/api/v1/query | python3 -m json.tool | grep -A2 variant
```

Очікуване: **blue ≈ 0.97, green ≈ 0.63**. Ось тепер можна починати.

## Крок 1. Показати топологію (3 хв)

```bash
kubectl -n ml-demo get pods -L variant
kubectl -n ml-demo get svc | grep ml-model
```

```
ml-model-5755fffc6b-9wkcj    1/1  variant=blue
ml-model-5755fffc6b-zz2x9    1/1  variant=blue
ml-model-green-58f5795649    1/1  variant=green

ml-model          selector: variant=blue     ← перемикач
ml-model-blue     selector: variant=blue     ← лише скрейп
ml-model-green    selector: variant=green    ← скрейп + ціль тіні
```

**Питання групі:** навіщо три Service, якщо трафік іде лише в один?

**Відповідь:** якби Prometheus скрейпив бойовий Service, то після перемикання
метрики blue **зникли б** — а дивитись треба саме на них, вирішуючи, відкочуватись
чи ні. Два окремі Service роблять скрейп незалежним від того, куди йде трафік.

## Крок 2. Green уже під моніторингом, хоч трафіку не має (3 хв)

Grafana → **ML-модель — моніторинг** → панель **«7в. Яка модель у якому варіанті»**:

```
variant   version   source
blue      8         registry
green     24        registry
```

Дві **різні моделі**, а не дві копії однієї. Blue читає `models:/iris-rf@champion`,
green — `@challenger`.

**Теза:** нову модель можна поставити поруч із бойовою, годувати її реальним
трафіком і дивитись на метрики — **не ризикуючи жодним користувачем**.

---

## Крок 3. Порівняти варіанти (5 хв)

Панель **«7а. Blue vs Green — запити за секунду»** — дві лінії приблизно по
4 rps. Blue тримає бойовий трафік, green — тіньовий: той самий payload летить в
обидва.

Панель **«5. Розподіл впевненості»** — ось де різниця кричить:

| | впевненість |
|---|---|
| blue (v8, f1 0.9800) | **0.97** |
| green (v24, f1 0.7119) | **0.63** |

**Питання групі:** ми ще нічого не перемикали. Звідки в green трафік?

**Відповідь:** `SHADOW_URL` у генераторі — той самий запит дублюється в обидва
варіанти. Тому різниця в передбаченнях є різницею **моделей**, а не наслідком
того, що їм дісталися різні квіти.

⚠️ Тінь вмикається `kubectl set env`, а **не** комітом у Git — інакше green
цілодобово отримував би 5 rps і засмічував панелі дашборда дріфту.

## Крок 4. АНТИПРИКЛАД: перемкнути руками (3 хв)

Найкраще демо GitOps у всьому курсі. Запускайте із секундоміром.

```bash
kubectl -n ml-demo patch svc ml-model -p '{"spec":{"selector":{"variant":"green"}}}'
kubectl -n ml-demo get svc ml-model -o jsonpath='{.spec.selector}{"\n"}' -w
```

**Зміряно: ArgoCD відкочує за 2 секунди.** Не за хвилину — за дві секунди.

**Теза:** у кластері не можна нічого «підправити руками» надовго. Git переміг.
Хочете змінити стан — змініть Git.

## Крок 5. Як треба: перемикання комітом (4 хв)

Один рядок у `k8s/model-api/service.yaml`:

```yaml
spec:
  selector:
    variant: blue      # ← міняємо на green
```

```bash
git commit -am "blue-green: перемикаємо трафік на green" && git push
kubectl -n argocd patch app ml-model --type merge \
  -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"hard"}}}'
```

**Зміряно: трафік перемикається за 4 секунди** після refresh. Без нього ArgoCD
опитує Git раз на 3 хвилини — на занятті це вічність.

Панель «Blue vs Green»: лінія blue падає **в нуль**, green подвоюється —
бойовий плюс тіньовий.

```
blue   0.00 rps
green  7.57 rps
```

### 🔴 Пастка, яка зʼїдає 10 хвилин заняття

```bash
curl -s localhost:8000/healthz     # покаже СТАРУ версію!
```

`kubectl port-forward svc/...` резолвить Service в **один под** на весь час
тунелю. Після перемикання старий тунель і далі стукає в blue.

Перевіряйте **зсередини кластера**:

```bash
kubectl -n ml-demo exec deploy/load-generator -- python -c \
  "import json,urllib.request; print(json.load(urllib.request.urlopen('http://ml-model.ml-demo.svc.cluster.local/healthz')))"
```

Або просто `make ports` заново.

## Крок 6. Відкат (3 хв)

Прод зараз обслуговує модель із впевненістю 0.63. Аварія. Відкочуємось:

```bash
git revert --no-edit HEAD && git push
kubectl -n argocd patch app ml-model --type merge \
  -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"hard"}}}'
```

**Зміряно: 5 секунд.** Поди blue **не перезапускались** — вони весь час
працювали, просто не отримували трафіку. Саме тому відкат миттєвий: нічого не
треба піднімати заново.

⚠️ `git revert -q` **не існує** — це не прапорець `git revert`. Команда мовчки
не спрацює, а ви думатимете, що відкотились. Перевірено на власній шкурі.

---

## Крок 7. Дві осі відкату (3 хв)

Найцінніша теза заняття.

```bash
git revert HEAD    # повертає ТРАФІК на blue
make rollback      # повертає МОДЕЛЬ на попередню версію
```

Blue-green керує тим, **який под відповідає**. Реєстр — тим, **яку модель цей
под завантажив**. Це різні осі.

**Питання групі:**

1. Проблема в **моделі** — яка команда?
2. Проблема в **новій версії образу сервісу** — яка?
3. Ви відкотили трафік на blue. Що станеться з green?

**Відповіді:** (1) `make rollback` — трафік ні до чого; (2) `git revert` —
модель ні до чого; (3) нічого, він і далі крутить кандидата й приймає тінь.
Відкат по не тій осі проблему не лікує.

## Прибирання після демо

```bash
make bluegreen-down     # прибрати green і вимкнути тінь
make train N=100 D=2    # повернути нормального чемпіона
```

⚠️ Перевірте, що `k8s/model-api/service.yaml` містить `variant: blue`, а
`git status` чистий. Забутий коміт із `variant: green` лишить прод на кандидаті
до наступного заняття.

## Якщо щось пішло не так

| Симптом | Причина | Дія |
|---|---|---|
| Панелі blue і green ідентичні | моделі однакової якості | гейт 1: `make train N=10 D=1 PROMOTE=false` |
| У green `source="baked"` | немає аліаса `@challenger` | те саме |
| Green без трафіку | тінь не ввімкнена | `make bluegreen-up` |
| Перемкнули — версія не змінилась | старий `port-forward` | `make ports` |
| `kubectl patch` відкочується | selfHeal, так і має бути | це крок 4, а не поломка |
| Метрики злились в одну лінію | немає `podTargetLabels` | перевірити `servicemonitor.yaml` |
| Панелі спорожніли | немає `jobLabel: app` | те саме |

## Зміряні числа для довідки

| Що | Скільки |
|---|---|
| selfHeal відкочує ручний patch | **2 c** |
| Перемикання комітом + refresh | **4 c** |
